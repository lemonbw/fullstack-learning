# Семантическое версионирование (SemVer)

Одним из популярных способов управления версиями является система SemVer.

SemVer определяет структуру версирования, которая делится на три части:

- major
- minor
- patch

и опциональные, дополнительные маркеры:

- pre-release
- build

Каждая из этих частей представляет собой число, полная версия приложения состоит из этих трёх частей, разделённых точкой:

major.minor.patch

А также опциональные маркеры:

major.minor.patch-pre-release+build

## Что за что отвечает?

### Major

Обновление major версии происходит, когда в приложении происходят изменения, включающие в себя "breaking changes". Такие изменения могут ломать обратную совместимость, из-за чего пользователям например приходится обновлять конфиги в соответсвии с новой версией приложения.

### Minor

Обновление minor версии происходит, когда вносятся новые функции, при этом сохраняя обратную совместимость.

### Patch

Обновление patch при исправлении ошибок. Сюда же можно записать изменения стилей, не добавляющих новую функциональность. Обновление patch не должно ломать обратную совместимость.

### Pre-release

Pre-release используется для обозначения предварительных версий приложения перед полноценным релизом. Такие версии могут содержать новую функциональность, которая ещё проходит тестирование и может измениться до выхода стабильной версии.

### Build

Build-метаданные используются для указания информации о конкретной сборке приложения. Они могут содержать номер сборки, идентификатор коммита, окружение или другие данные, помогающие различать разные сборки одной версии.

---

## Правила обновления версий

При увеличении major версии minor и patch сбрасываются в ноль:

```
1.4.5 → 2.0.0
```

При увеличении minor версии patch сбрасывается:

```
1.4.5 → 1.5.0
```

Patch увеличивается при совместимых исправлениях:

```
1.4.5 → 1.4.6
```

Pre-release и build являются дополнительными идентификаторами версии и указываются только при необходимости, например для тестовых версий или информации о конкретной сборке.

## Полезные советы

### Начальная версия проекта

При начале разработки проекта обычно используют версию 0.1.0, так как приложение ещё находится в активной разработке и его API или функциональность могут изменяться без сохранения обратной совместимости.

Версия 1.0.0 обычно означает первый стабильный релиз.

### Changelog

Структурированно и понятно описывайте изменения в Changelog. Это полезно для вас, пользователей и других разработчиков.

### Git-теги

Создавайте теги для релизных версий. Это поможет легко найти код конкретной версии, связать версию с коммитом, а также упростит работу с CI/CD.
